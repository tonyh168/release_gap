## 背景分析

原报告中 V1–V4 评测数据全空，说明服务在 V1 就崩了。Issues 包含三条：
`Operator crash`、`Operator accuracy degradation`、`Operator performance degradation`——
说明即使部分版本起了服务，精度和性能也有问题，是一个综合型难题。

GLM-4-32B-0414 使用 GLM 特有的 RoPE + 双流 attention 架构，vLLM 对 GLM4 有专门的 model
实现，需要确认 `--trust-remote-code` 是否足够，或是否需要额外的 attention backend 参数。

TP 计算：32B bf16 ≈ 64GB → 单卡 63.6GB 放不下 → **TP=2 起步**（127.2GB，预留后可用 89GB）。
原报告显示 9 张卡，属于意外情况（通常 8 卡）；本次按 TP=4 上机，稳妥留余量。

## Step 3：起 vLLM 服务

### 修复策略

双重问题（crash + 精度），分阶段处理：
1. **第一阶段**：先关 plugin（`VLLM_PLUGINS=` 不设）起 V1 裸 vLLM，确认能起来作为基线
2. **第二阶段**：开 plugin-FL，用默认黑名单，看 crash 日志补充黑名单
3. **第三阶段**：服务起来后评测，若精度不达标用二分法定位退化算子

### 环境变量（每次迭代更新）

**第1次：裸 vLLM（V1 基线，不开 plugin）**：
```bash
# 不设 GEMS_VENDOR / VLLM_PLUGINS，验证裸 vLLM 能起
export MACA_VISIBLE_DEVICES=0,1,2,3
export VLLM_WORKER_MULTIPROC_METHOD=spawn
export VLLM_ENGINE_ITERATION_TIMEOUT_S=7200
export VLLM_EXECUTE_MODEL_TIMEOUT_SECONDS=7200
```

```bash
model_name=GLM-4-32B-0414
mkdir -p /models/release_run_logs/${model_name}
vllm serve /models/GLM-4-32B-0414 \
  --served-model-name ${model_name} \
  --dtype bfloat16 \
  --tensor-parallel-size 4 \
  --max-model-len 32768 \
  --gpu-memory-utilization 0.9 \
  --port 8000 \
  --enforce-eager \
  --no-enable-chunked-prefill \
  --trust-remote-code \
  2>&1 | tee /models/release_run_logs/${model_name}/serve_v1.log
```
